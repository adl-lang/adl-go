# goadlc

`goadlc` generates Go source from [ADL](https://github.com/adl-lang/adl) declarations. It
is itself written in Go, and it is **self-hosting**: its own configuration types, and the
ADL runtime's `sys.adlast` AST types that it walks, are generated by running it. A change
to the generator is checked by regenerating the tree and diffing.

```sh
go run main.go -cfg ./cfgs/goadlc.v2.cfg.json     # regenerate goadlc's own config types
go run main.go -cfg <cfg.json> -debug             # verbose: files read, files written
go run main.go -cfg <cfg.json> -dump-config       # print the config as JSON and exit
```

The `adlc` binary (the Haskell ADL compiler) must be on `PATH` - goadlc shells out to it
for parsing. `flake.nix` at the repo root pins 1.2.3. `task gen` at the repo root runs
every generation the repo depends on; `Taskfile.local.yml` here holds goadlc's three.

---

## 1. The shape of the thing

Five stages, each owned by one package under [internal/cli/](internal/cli/):

```
  cfg.json ──► root      decode the config into a pre-wired object graph
               ▼
               loader    shell out to adlc, read back the AST as sys.adlast values
               ▼
               gomod     find go.mod: module path + root dir
               ▼
       ┌───────┴────────┐
    gotypes           goapi        one sub-task per kind of output
       └───────┬────────┘
               ▼
               gogen     resolution: ADL TypeExpr ─► Go type, ADL value ─► Go source
               ▼
            templates    layout: one {{define}} per params struct
               ▼
            goimports    which imports the rendering actually used
               ▼
            .go files    gofmt'd, written
```

[main.go](main.go) does three things and nothing else: construct that graph, parse three
flags, call `GenGo.Run()`.

| package | what it owns |
|---|---|
| [root](internal/cli/root/) | `Root` (debug/cfg/dump-config) and the config read/dump |
| [loader](internal/cli/loader/) | ADL sources ➜ `LoadResult` (modules + combined AST + resolver) |
| [gomod](internal/cli/gomod/) | go.mod discovery ➜ `ModulePath`, `RootDir` |
| [gengo](internal/cli/gengo/) | the top-level config object; `Run()` sequences the stages |
| [gotypes](internal/cli/gotypes/) | the types sub-task: `<pkg>.go` and `<pkg>_ast.go` per module |
| [goapi](internal/cli/goapi/) | the api sub-task: `<pkg>_srv.go` for an ADL http api struct |
| [gogen](internal/cli/gogen/) | the generator core: type resolution, value emission, file writing |
| [templates](internal/cli/templates/) | the one template set; all layout lives here |
| [goimports](internal/cli/goimports/) | import set with alias-collision handling |

Each of `root`, `loader`, `gomod`, `gengo`, `gotypes`, `goapi` holds **three files**:

- `x.go` - *generated* from [adl/goadlc/cli/x.adl](adl/goadlc/cli/), the config struct
  with its `Make_` constructors and `Default_` funcs. Never edit.
- `x_ast.go` - *generated*, the `Texpr_X` / `AST_X` functions and the `init()` that
  registers them with `adl.RESOLVER`. Never edit.
- `x_fn.go` - hand-written, the behaviour hung off the generated struct.

So the config schema is ADL, the config parser is generated from that ADL by goadlc, and
goadlc reads its own config with it.

## 2. Config: a decode onto a pre-wired graph

The config file is a JSON encoding of `cli.gengo.GenGo`
([adl/goadlc/cli/gengo.adl](adl/goadlc/cli/gengo.adl)). A minimal one:

```json
{
  "Loader": { "Searchdir": ["adl"], "MergeAdlext": "adl-go",
              "Files": ["adl/**/*.adl"] },
  "Mod":    { "Outputdir": "." },
  "GoTypes":{ "GoAdlPath": "github.com/adl-lang/adl-go/adl",
              "Outputdir": "generated" }
}
```

`ReadConfig` ([root_fn.go](internal/cli/root/root_fn.go)) decodes it through
`adl.CreateJsonDecodeBinding(gengo.Texpr_GenGo(), adl.RESOLVER)` - the same ADL JSON
machinery any generated type gets, driven by the AST that `gengo_ast.go`'s `init()`
registered.

The subtlety worth knowing before touching [main.go](main.go): **the decode is a merge,
not a construction.** `main` builds and cross-wires the object graph first (`ld.Root = rt`,
`gt.Root = rt`, `gg.Loader = ld`, ...), then decodes the file over it. Two properties of
the ADL decoder make that work, and both are load-bearing:

- A `Nullable<T>` field whose pointer is already non-nil decodes **in place**, so the
  `Root` back-pointers inside a pre-built `Loader` survive the decode of `"Loader"`.
- A field marked `@SerializedName "-"` is never read from JSON; it falls through to its
  ADL default, and a `= null` default on a `Nullable` is a no-op for the same reason.

That is why the `root`, `loader` and `goMod` fields in the `.adl` files all carry
`@SerializedName "-"` and `= null`: they are wiring, not configuration. `-dump-config`
(`DumpConfig`) round-trips the value the other way, so the flags and the file describe
exactly the same type.

The remaining wiring - the parts that only exist after a stage has run - happens in
[gengo_fn.go](internal/cli/gengo/gengo_fn.go): `Run()` hands the `LoadResult` and
`GoModResult` to each sub-task before calling it.

### Templated defaults

Two `Loader` fields default to a template rather than a value:

```adl
String WorkingDir   = "{{.OS.MkdirTemp \"\" \"goadlc-\"}}";
String UserCacheDir = "{{.OS.UserCacheDir}}";
```

`tmplVar` in [main.go](main.go) executes both through `gotmpl` against a `Data{OS *OS}`
whose methods wrap `os.MkdirTemp` / `os.UserCacheDir`. This runs after the config decode,
so a config file can override either with a literal path - at the cost that any value of
those two fields is template-expanded, brace characters included.

## 3. Loading: adlc, twice

[loader_fn.go](internal/cli/loader/loader_fn.go) turns file patterns into
`sys.adlast.Module` values.

1. **Bundle maps** (`BundleMaps`) map an ADL module-name prefix to a Go module path, and
   say where that bundle's sources live. `file://` sources are appended to the adlc
   search path; `https://….zip` sources are downloaded to `<UserCacheDir>/download/…`
   and unpacked to `<UserCacheDir>/cache/…` once, then reused.
2. **Patterns** in `Files` get `$VAR` expansion (with `$ADLSTDLIB` resolved by running
   `adlc show --adlstdlib` when unset) and are globbed with `zglob`, sorted for
   determinism.
3. **adlc runs twice.** First `adlc ast --outputdir <wd>/individual` - the file names it
   drops there are the definitive list of *which modules were asked for*, i.e. what to
   generate. Then `adlc ast … --combined-output=combined.json`, which contains those
   modules **plus everything they import**. The combined file is decoded with the ADL
   runtime into `map[string]adlast.Module`.

The result is `LoadResult{CombinedAst, Modules, Files, BundleMaps}`, where `Modules` is
"generate these" and `CombinedAst` is "resolve against these". `LoadResult.Resolver`
serves `ScopedName ➜ Decl` out of `CombinedAst`, falling back to `adl.RESOLVER` - the
ASTs compiled into the runtime - so `sys.types`, `sys.adlast` and `adlc.config.go_`
resolve even when they were not passed as input.

`MergeAdlext: "adl-go"` is passed through to adlc as `--merge-adlext`, which is how a
`foo.adl-go` file adds Go-specific annotations (e.g. `go_custom_type`) to `foo.adl`
without either file knowing about the other. See
[adl/stdlib_go/sys/types.adl-go](adl/stdlib_go/sys/types.adl-go).

## 4. Generating: params structs in, templates out

Both sub-tasks follow the same shape, and it is the heart of the design:

> **Go decides *what*; a template decides *how it looks*.**
> Go resolves types, decodes annotations and tracks imports, then packs the answers into
> a small `xxxParams` struct. Each params struct has one `{{define "xxxParams"}}` named
> after it. Templates hold every brace, comma and newline of the output.

### One file, one template call

[gogen_writefile.go](internal/cli/gogen/gogen_writefile.go) executes exactly one
template - `"file"`, in [gengo.tmpl](internal/cli/templates/gengo.tmpl) - per generated
file, then runs `go/format` over the result (unless `NoGoFmt`; on a format error it
writes the unformatted bytes and complains to stderr, which surfaces as a regen diff
rather than a silent pass).

The import block sits above the body, but *which imports a file needs is only discovered
while the body renders* - `GoType`, `GoValue` and `GoImport` each register into `Imports`
as a side effect. [FileParams](internal/cli/gogen/gogen_file.go) resolves that ordering:
`.Imports` forces `.Body()` first, `.Body()` caches, and by the time the import block is
written the used-set is complete.

```
  {{define "file"}}
      package .Pkg
      import ( .Imports )   ← forces ↓, then filters Specs by Used
      .Body                 ← renders BodyTmpl over BodyData, cached
```

### The template set

[templates.go](internal/cli/templates/templates.go) embeds every `*.tmpl` into **one**
set, so a define in one file can call a define in another. It is built on
[gotmpl](https://github.com/millergarym/gotmpl), a fork of `text/template` aimed at code
generation. Two of its additions are used here:

- **`tmpl_by_type`** dispatches on a value's runtime type name:
  `{{tmpl_by_type .Decl.Type_.Branch.V "decl_" ""}}` renders an `adlast.Struct` with
  `decl_Struct`, a `Union` with `decl_Union`, and so on. An ADL union branch becomes a
  template, not a Go type switch. `genapi.tmpl` uses the same mechanism over the
  heterogeneous `[]any` of service methods.
- **`WithDynamicScopedVars`** makes a caller's `$vars` visible in the templates it
  invokes. That is how `decl_Struct` - whose `dot` is the branch payload - still reaches
  `$P` (the decl params) and `$G` (the generator). The cost: a mistyped `$V` is a nil at
  execution time rather than a parse error, so the regen diff is what catches it.

Plus two funcs, `public` and `lower`.

### gotypes: `<pkg>.go` and `<pkg>_ast.go`

[gotypes_fn.go](internal/cli/gotypes/gotypes_fn.go) runs one goroutine per module
(`errgroup`). Each module gets **two** `Generator`s - one per output file - so the two
files accumulate independent import sets. Decl names are sorted before rendering.

| file | body template | per decl |
|---|---|---|
| `<pkg>.go` | `gotypes_decls_body` | the Go type, `MakeAll_`, `Make_`, `Default_` funcs; unions also get `Cast_`, `Handle_`, `HandleWithErr_` |
| `<pkg>_ast.go` | `gotypes_ast_body` | `Texpr_X()`, `AST_X()` and an `init()` registering both with `adl.RESOLVER` |

Two decls generate nothing in the first file: one carrying a `go_custom_type` annotation
(the Go type already exists by hand) and a **generic** type alias (Go has no
`type X[A any] = …`). Both still get AST entries.

`ExcludeAst: true` suppresses the second file. `StdLibGen: true` is the bootstrap switch:
for `sys.adlast`, `sys.types` and `adlc.config.go_` the AST file is emitted into the
`adl` package itself with a dot-import of the module, because the runtime cannot import
the package that defines its own resolver.

An ADL struct becomes a wrapper over an unexported twin:

```go
type StructOfPrimitives struct{ _StructOfPrimitives }

type _StructOfPrimitives struct {
    A int32 `json:"A"`
    ...
}
```

which is what lets the generated `Make_` constructors be the only way to build a value
with defaults applied.

### goapi: `<pkg>_srv.go`

[goapi_fn.go](internal/cli/goapi/goapi_fn.go) starts at one struct named by
`ApiStruct` and walks its fields depth-first, following `CapabilityApi<C,S,V>` fields and
plain references to other api structs, expanding type aliases as it goes. Every api it
reaches yields a pair: an `X_Service` interface (one method per `HttpGet` / `HttpPost` /
sub-api field) and a `Register_X(mux, srv, …)` func that wires the handlers into a
`http.ServeMux`. `C`, `S` and `V` are reserved names; the DFS rejects a field, struct or
type param that collides with them.

## 5. gogen: the two hard parts

Everything the templates call `$G.` on lives here.

### ADL type ➜ Go type

[gogen_adl2go.go](internal/cli/gogen/gogen_adl2go.go). `GoType(typeExpr, anns)` returns a
**structured** `goTypeExpr{Pkg, Type, TypeParams, UnionTypeParams, IsTypeParam}`, not a
string, so a template can ask for the parts: `{{$type.UnionTypeParams.RSide}}`. It:

- maps the 15 ADL primitives (`primitiveMap`, plus `Vector` ➜ `[]T`, `StringMap` ➜
  `map[string]T`, `Nullable` ➜ `*T`, `TypeToken` ➜ `adlast.ATypeExpr[T]`);
- redirects a `go_custom_type`-annotated reference to the hand-written Go type, adding
  its import;
- **monomorphises** generic type aliases through `CreateDecBoundTypeParams` +
  `SubstituteTypeBindings`, since Go cannot express them;
- adds an import for any reference into another module, via `Imports.AddModule`;
- collects the type params it meets into `unionTypeParams`, which is what the union
  branch wrapper types are parameterised by.

[gogen_type_params.go](internal/cli/gogen/gogen_type_params.go) holds `TypeParam` and its
renderings: `LSide()` = `[A any, B Ord]` (declaration side, honouring the
`TypeParamConstraintList` annotation), `RSide()` = `[A,B]` (use side), plus `TexprArgs` /
`TexprValues` for the `Texpr_` functions.

### ADL value ➜ Go source

[gogen_adl2go_val.go](internal/cli/gogen/gogen_adl2go_val.go). Used for two things: a
field's `Default_` body, and the entire `AST_X()` literal - the AST files are a decl
value printed as Go source.

The value is first round-tripped through the ADL JSON encoder into `any`, then walked
against its `TypeExpr`: primitives print themselves, a struct emits a `MakeAll_` call, a
union a `Make_X_branch` call, a newtype a conversion, a custom type a
`adljson.Unwrap(((*Helper)(nil)).Construct(…))` call with a reconstructed `TypeExpr` per
type parameter. `genAdlAst` switches on one special case: a field literally named
`annotations` renders as a `customtypes.MapMap[adlast.ScopedName, any]` literal, its
entries sorted by rendered text so the generated AST is stable.

The walk carries a `path []string` purely so a panic can name the field it died on.

### Imports

[goimports/imports.go](internal/cli/goimports/imports.go). Each sub-task declares
`ReservedImports()` - the packages generated code may refer to by short name, so a
template can write `{{$G.GoImport "fmt"}}Errorf(…)` and get back `"fmt."` while the spec
gets marked used. `AddModule` turns an ADL module name into an import path: a matching
`BundleMap` prefix wins, otherwise it is `<go.mod module path>/<midPath>/<module/as/dirs>`
where `midPath` is the output dir's offset below the go.mod root. Name collisions are
resolved by aliasing (`http`, `http2`, `http3`, …).

## 6. Adding to the generator

The grain of the code is: **add a params struct in Go, add a `{{define}}` with the same
name.** Concretely, to change what is emitted:

1. Find the params struct whose name matches the `{{define}}` you want to change
   (`internal/cli/*/​*_params.go`, or beside the code that builds it).
2. Layout-only change? Edit the `.tmpl`. New information needed? Add a method or field to
   the params struct - methods are preferred, since `declParams.Fields()` and friends keep
   the derivation next to its use.
3. New ADL union branch to render? Add a `{{define "prefix_BranchType"}}`; `tmpl_by_type`
   finds it by name.

Then run the verification loop. goadlc generates its own source, so this is exact:

```sh
task gen                  # gen_texpr, gen_adlast, gen_goadlc, gen_stdlib, gen_exer
task tests:gen_api
git diff --exit-code      # generated output must be byte-identical
task test                 # tests/ and goadlc/
```

Two unit test files cover what the regen cannot reach - `strRep`, annotation entries and
the qualified custom-type helper registration, none of which occur in the ADL the build
regenerates: [gogen_adl2go_val_test.go](internal/cli/gogen/gogen_adl2go_val_test.go) and
[gogen_customtype_test.go](internal/cli/gogen/gogen_customtype_test.go).

### Bootstrap order

`sys.adlast` is generated by the generator that walks `sys.adlast` values. If a change
touches the AST types themselves, regenerate in the order `task gen` uses - texpr
primitives, then `adlast`, then goadlc's own config, then the stdlib - and expect to build
against the previous generator once before the new output is usable.

## 7. Design history

The current arrangement arrived in three documented steps, each in the repo root:
[plan.md](../plan.md), [plan2.md](../plan2.md) (one `ExecuteTemplate` call per generated
file, killing the string-returning `RenderString` hop) and [plan3.md](../plan3.md) (the
emission methods on `Generator` become `{{define}}` blocks; in progress). Read plan3
before moving anything between Go and a template - it sets out which computations stay in
Go and why. [suggestions.md](../suggestions.md) lists cleanups that sit outside those
plans.
